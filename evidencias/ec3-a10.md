## Decisión de permisos
- Rutas autenticadas: GET /api/tasks, GET /api/tasks/:id, POST /api/tasks, PATCH /api/tasks/:id, PATCH /api/tasks/:id/complete
- Ruta exclusiva de admin: DELETE /api/tasks/:id
- Justificación: el JWT verificado aporta la identidad del usuario; cualquier usuario autenticado puede ejecutar operaciones de CRUD de tareas, pero la eliminación queda restringida al rol admin para evitar que un usuario normal borre recursos ajenos.

## Preguntas de cierre
1. ¿Por qué un token decodificable no necesariamente es un token válido?
   Un JWT decodificado puede ser manipulado si no se verifica la firma y los claims esperados. La validación real debe comprobar firma, emisor, audiencia, expiración y formato.
2. ¿Cuándo corresponde responder 401 y cuándo 403?
   401 cuando no hay autenticación válida o está mal formada; 403 cuando la identidad sí existe pero no tiene permiso para esa operación.
3. ¿Por qué CORS no sustituye la autenticación?
   CORS solo restringe qué orígenes del navegador pueden leer la respuesta; no valida que el cliente sea quien dice ser.
4. ¿Qué riesgo existe si DELETE se registra antes de requireRole?
   Un usuario autenticado podría borrar tareas aunque no sea admin, porque la autorización nunca se ejecuta antes de la operación.
5. ¿Por qué debes iniciar sesión después de cambiar el rol en MongoDB?
   El token se firma con el rol válido al momento del login; un token anterior conserva el rol viejo hasta que se renueve.
6. ¿Cómo llega un error asíncrono de authenticate al errorHandler en Express 5?
   `authenticate` es async y devuelve una promesa; si `verifyAccessToken` rechaza, Express 5 propaga ese rechazo al middleware central `errorHandler` sin necesidad de un `try/catch` que oculte el error.
7. ¿Qué limitación tiene el almacén en memoria del rate limiter al escalar la API?
   El contador se mantiene por proceso y no se comparte entre varias instancias, por lo que en una API escalada se requiere un store distribuido.
8. ¿Qué cambios requeriría autorizar por propietario de la tarea?
   Habría que comparar `res.locals.auth.userId` con el propietario original de la tarea y permitir el acceso solo si coinciden o el usuario es admin.

## Reflexión
El punto más importante fue entender la diferencia entre autenticación y autorización: un token válido solo prueba la identidad, pero no garantiza que la persona pueda borrar o modificar recursos. La prueba más útil fue validar que `DELETE` devuelve 403 para un usuario normal y que el cambio de rol requiere un nuevo login para actualizar el JWT.
